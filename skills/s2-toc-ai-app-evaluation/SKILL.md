# S2 ToC AI 应用测评

用最低成本先建立判断，仅在明确卡住或产品具备战略重要性时升级投入。

## 开始前

确认或从上下文推断：

1. 测评对象与竞品范围。
2. 目标深度：默认 L1；L2、L3 是彼此独立的可选维度，不要求顺序升级。
3. 是否有试用账号、地区限制、付费预算和可操作环境。
4. 目标读者、截止时间与发布位置。默认发布结构为 Hi 文档父索引加产品子文档；没有相应工具或权限时，先产出可直接粘贴的文档并说明限制。

除非缺失信息会造成高成本、付费、外部发布或明显偏离目标，否则先按合理假设推进，并在报告开头写明假设。

## 选择深度

| 情况 | 执行 |
|---|---|
| 常规竞品扫描、产品多、时间有限 | L1 |
| 需要验证官方宣传与真实口碑，或公开资料无法解释关键分歧 | L1 + L2 |
| 产品对业务或赛道有战略意义 | L1 + L3 |
| 同时需要战略判断和真实口碑验证 | L1 + L2 + L3 |

不要把 L3 写成更长的 L1。L3 必须回答团队的核心论点、为什么是现在、做成后的价值以及壁垒落在哪几层。

## 执行 L1

先按以下顺序建立判断，再写报告：

1. 建立竞品/同类头部产品参照系。
2. 扫描国内外社媒讨论声量，允许“太早期、看不清”成为正式结论。
3. 能试用时亲自上手并记录直觉。
4. 对照 buy-in 人群画像与不 buy-in 人群吐槽，找出真实分歧点与天花板。
5. 可行时低成本征询身边多样化样本，校准个人直觉。

不盲目发起正式访谈。先完成开放资料检索；只有仍卡住时才建议或执行访谈。

### 选择测试模式

- 有试用权限：设计 3–6 个覆盖不同能力维度的任务，完整记录 Prompt、输入、输出、耗时、成本、失败和成功。不要只展示高光。
- 无法试用：用官网、官方文档、GitHub、定价页、媒体与用户渠道做桌面研究。对事实、推论、信息缺口进行克制而明确的标注。
- 部分可用：核心功能实测，团队、融资与背景走研究模式。

测试场景不得凭空编造。优先从官网/定价页反复强调的场景、真实用户高频用法、帮助文档与 FAQ 反推。把 issue 改写为可执行的正向任务；详见 [references/evaluation-playbook.md](references/evaluation-playbook.md)。

团队背景用时间轴呈现创始人姓名、教育、工作/创业经历与联合创始人渊源，并尽量附可验证来源。

## 判断是否加做 L2

出现任一信号即可加做：

- 产品太新或小众，公开讨论不足。
- buy-in 与不 buy-in 的分歧无法由现有评论解释。
- 核心问题需要懂行用户或头部玩家的判断。
- 对标、声量扫描和实测后仍无法回答核心问题。

先扩大公开检索，再考虑一对一访谈。若产品已有足够真实社区讨论，也可直接用 L2 验证口碑，无需等 L1 “失败”。

## 执行 L2

只收集未被产品方筛选的真实用户一手声音；官网证言墙只能作为官方说法，不能冒充用户口碑。

1. 确认产品旧名、新名、公司名、创始人名与同名噪声。
2. 用查询矩阵批量检索：主体词 × review、complaints、alternative、即刻、小红书、GitHub issues、融资等意图词。
3. 优先深挖官方社区/Discord（若可访问），同时检索正负面词并观察团队响应。
4. 每条引用记录渠道、作者、时间和可访问链接；好坏都收录，按频率与严重度排序。
5. 多渠道重复出现的痛点标为高置信度共识，单渠道标为个案。
6. 明确列出核查过但未找到或无法访问的平台。

信源优先级：官方社区中的真实用户讨论 > 独立社交媒体发言 > 第三方评测博客 > 官网证言墙。自选择偏差仍需说明。

输出：一页结论、按信源分组的好评/痛点、覆盖盲区、官方与第三方说法对照、不过度外推的用户画像、投资视角结论和待验证清单。

## 执行 L3

仅在产品具备战略重要性且能找到足够一手材料时执行：

1. Highlights：一句话结论、为什么现在、底层哲学、需要在哪几层做功、壁垒候选。
2. 产品定义：一句话定位和必要的概念/实体关系图。
3. Step by Step：从注册到核心功能的完整流程截图。
4. 高光 Case：优先从真实 dogfooding 日志或录屏提取意外高光，说明发生了什么、体现何种能力、与普通任务的差别。
5. 创始人思想：从博客/访谈提炼反常识或有洞察的原始论点，需要时中英对照。
6. 深度履历：补充能证明能力形成过程的细节，而非堆砌头衔。

“为什么重要”必须来自创始人真实博客、访谈或演讲。找不到时，明确判定材料不足，不硬做成熟度假象。团队自述的壁垒必须用第三方证据或 L2 用户反馈交叉验证。

## 证据规则

对所有关键事实执行三方交叉验证：

- 一级：融资、用户规模、创始人核心履历、核心技术声明至少需要两个独立且类型不同的信源。
- 二级：官网功能描述、单条用户评论可单源使用，但标明来源性质。
- 三级：报告自身分析标为【推论】，并检查内部一致性。

信源类型包括一手信源、权威第三方信源、社区/用户信源。两个同源转载不算两个独立信源。

出现冲突时不要静默选边：列出冲突，给出带【推论】的解释；无法调和则标为【信息缺口】并列入待核实项。

## 写作与交付

- 先结论，后证据；敢于判断，不只罗列功能与评论。
- 研究模式开篇用一张 highlight 卡片浓缩“人 + 产品 + 关键判断”。
- 用彩色小标题、短句和清晰分段；不要逐句堆标签和链接。
- 只在真正推断处使用【推论】，保持正文干净。
- 单份文档预计超过 5,000 字时，优先拆分为子文档。
- 使用 [references/report-templates.md](references/report-templates.md) 选择对应模板，并在交付前完成检查清单。
