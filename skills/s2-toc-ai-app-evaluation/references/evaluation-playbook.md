## 1. 五步基础判断面

### 1.1 竞品参照

先选择 2–4 个参照物，至少覆盖：

- 同类头部产品：定义用户预期上限。
- 直接竞品：比较核心工作流。
- 邻近替代品：判断用户是否真的需要 AI 产品。

比较维度优先选择用户价值、完成质量、时间成本、金钱成本、可靠性、学习成本和留存理由，不要只比功能数量。

### 1.2 声量扫描

扫描官方渠道、真实用户社区、独立评测和中文/英文社媒。记录：

- 讨论量级与时间分布。
- 讨论是否由发布、融资、KOL 或真实留存驱动。
- 独立用户内容与官方转发内容的比例。
- 是否存在改名、同名产品或关键词污染。

低声量是阶段判断，不自动等同于产品差。

### 1.3 亲自上手

首次体验保留未经解释的直觉记录，再做系统测试，避免研究材料反向污染首因体验。记录首次价值出现时间、关键阻力、意外高光和无法容忍的失败。

### 1.4 Buy-in 对照

不要问笼统的“用户喜不喜欢”。分组回答：

- 买单者是谁？他们原本用什么？为什么现在换？高频使用场景是什么？愿意付出的时间/价格是多少？
- 不买单者是谁？卡在价值、质量、可靠性、隐私、价格、学习成本还是工作流迁移？
- 两组分歧由产品能力、用户需求强度、使用方法或阶段成熟度中的哪一项解释？
- 分歧是否揭示目标用户边界、增长天花板或定位错误？

### 1.5 低成本校准

身边样本用于校准直觉，不代表总体。尽量覆盖不同年龄、职业、AI 熟练度和需求强度。记录样本构成，不把便利样本外推为市场结论。

## 2. Use Case 挖掘与设计

### 2.1 基础来源

按以下顺序找真实场景：

1. 官网首页与定价页反复强调的 2–3 个场景。
2. 真实用户社区中的“产品用来做什么”与成果展示。
3. 官方帮助文档和 FAQ 暗示的常见任务或卡点。

把故障描述转为任务：

- 避免：换设备后 Gmail 断线，助手读不到新邮件。
- 采用：测试 Gmail/Calendar OAuth 授权、跨设备连接和断开后重新授权的便捷程度，评估 24/7 无人值守场景的可靠性。

### 2.2 任务组合

设计 3–6 个任务，尽量覆盖：

- 首次上手与价值到达速度。
- 核心高频任务。
- 边界或复杂任务。
- 多步骤/长上下文/跨工具能力。
- 失败恢复与可靠性。
- 价格或配额敏感场景。

每个任务记录：

| 字段 | 内容 |
|---|---|
| 用户目标 | 用户真正想完成什么 |
| 场景来源 | 官网、用户评论、FAQ、dogfooding 等 |
| 完整输入 | Prompt、文件、设置和前置条件 |
| 成功标准 | 可观察、可比较的判定条件 |
| 输出 | 原始输出或可追溯截图/链接 |
| 耗时与成本 | 人工时间、机器时间、价格/额度 |
| 结果 | 成功、部分成功、失败 |
| 观察 | 高光、缺陷、恢复成本 |

### 2.3 进阶场景

仅在产品足够复杂或执行 L3 时增加。优先从真实 dogfooding 日志、公开录屏或用户复盘中打捞意外高光，而非刻意设计 demo。

每个高光必须回答：

1. 发生了什么？
2. 体现了什么能力？
3. 与普通任务的差别在哪里？
4. 能否复现，证据是什么？

第三问决定案例是否值得单独呈现。

## 3. 渠道策略

渠道可访问性会变化，执行时先快速复核。默认经验优先级：

1. Capterra、TrustRadius、Product Hunt：通常可取得较完整评论和 Pros/Cons、迁移原因等结构化信息。
2. 小红书：适合中文真实体验，但必须处理同名噪声。
3. Reddit：若页面或 API 受限，使用搜索摘要仅作线索，不把截断摘要当完整引用。
4. Twitter/X：若环境不可访问，明确列为覆盖盲区，不用二手转述伪装成直接检索。

对所有渠道分别记录“找到”“未找到”“不可访问”，避免把覆盖缺失写成没有负面反馈。

## 5. L2 检索 SOP

### 5.1 消歧

列出产品名、域名、公司名、旧名、创始人、核心功能关键词和排除词。逐条核对评论中的功能描述，防止把同名产品评论混入。

真实踩坑模式：同名 SaaS 与 Mac 软件、消费品牌、人物或普通名词共享关键词。名称命中不等于产品命中。

### 5.2 查询矩阵

组合：

- 主体：产品名、旧名、公司名、创始人名。
- 意图：review、complaints、alternative、pricing、cancel、migrate、bug、即刻、小红书、GitHub issues、融资。
- 场景：产品核心用例关键词。

### 5.3 官方社区

若能访问 Discord、论坛或 GitHub：

- 搜负面词：bug、broken、slow、refund、cancel、privacy、fail。
- 搜正面词：love、saved、workflow、daily、recommend、success。
- 记录团队是否回应、回应速度、是否解决、是否反复发生。

### 5.4 归纳

- 先保存原始证据，再编码主题。
- 区分频率与严重度：低频数据丢失可能比高频 UI 抱怨更重要。
- 多渠道独立重复出现才升级为共识。
- 把具体评论的作者/时间/渠道保留在引用旁。
- 用户画像只覆盖样本，不外推整体市场。

## 6. L3 高光与创始人思想

优先搜索创始人博客、长访谈、演讲、播客和产品 dogfooding 记录。提炼：

- 团队相信但行业尚未形成共识的论点。
- 为什么技术、成本、分发或用户行为在此刻发生变化。
- 产品需要在模型、数据、工作流、交互、分发或社区的哪些层做功。
- 哪些层难做，以及是否有第三方证据证明壁垒。

找不到足够一手思想材料时，不用媒体简介补写“哲学”，明确说明 L3 条件尚不成立。

## 7. 升级决策

完成 L1 后问：

1. 最关键的投资/产品问题是否已经能回答？
2. 不确定性来自缺少公开口碑，还是缺少战略一手材料？
3. 新增投入是否可能改变当前结论？

- 缺真实口碑：加 L2。
- 缺战略论点且产品重要：加 L3。
- 两者都缺且重要：两者都加。
- 新增投入不太可能改变结论：停止升级，明确剩余不确定性。

访谈是公开检索后的最高成本升级项。建议明确目标人群、需要解决的问题和“什么答案会改变结论”后再执行。
